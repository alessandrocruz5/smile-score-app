- `src/lib/session.ts`. These are **the** two helpers every page, route handler and action uses (the PLAN rule:
  every server component, route handler and server action that touches user data checks the session itself,
  because of CVE-2025-29927):
  ```ts
  import { cache } from "react";
  import { headers } from "next/headers";
  import { redirect } from "next/navigation";
  // cache(): the layout and the page both check the session; this makes it one DB lookup per request
  export const getSession = cache(async () => {   // route handlers: null -> they return 401
    return auth.api.getSession({ headers: await headers() });
  });
  export async function requireSession() {        // pages + server actions: redirect if none
    const session = await getSession();
    if (!session) redirect("/login");
    return session;
  }
  ```
  Export the session type: `export type Session = NonNullable<Awaited<ReturnType<typeof getSession>>>`.
- `src/proxy.ts`. Next 16 renamed `middleware.ts` to `proxy.ts`, and the exported function to `proxy`. VERIFY in the
  Next 16 docs. It handles **optimistic UX redirects only**: no DB call, no real auth. Use `getSessionCookie(request)`

  - **no** cookie-based redirect away from `/login` or `/register` **(audit)**. `getSessionCookie` only checks that a
    cookie exists. A stale cookie (DB reset, expired or revoked session, the M5 wipe) would then bounce
    `/login` → `/dashboard` (proxy) → `/login` (`requireSession`) forever. The `/` page (09) does the real
    `getSession()` redirect instead.

  - Write a top-of-file comment that it's UX only, that enforcement lives in `requireSession()` and `getSession()`,
    and why `/login` isn't redirected (the stale-cookie loop).
